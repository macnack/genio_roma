# Tricks and best practices (DX-M1 toolchain)

Consolidated tips, pitfalls and gotchas collected from the official `.deepx/` agent knowledge base (common_pitfalls, sdk_grounding_reference, toolsets, instructions) and official docs. Grouped by pipeline stage: export, compile, calibration, runtime, performance, debugging. See [CONVENTIONS.md](CONVENTIONS.md) for claim classes and citation rules, and [agent_dev.md](agent_dev.md) for how these files are organised.

Source note: the `.deepx/memory/*.md` files are written by DEEPX for AI agents. They are official repo content but several entries are agent-behaviour rules rather than SDK facts; those are tagged "(agent rule)" below. Abbreviations used in citations: `dx-compiler@a087726ead v2.5.0`, `dx-runtime@73ff9904f5 v2.5.0`, `dx-all-suite@51d81fe2ef v2.5.0`, `dx_app@375de0344f v3.3.0`.

## Officially documented facts

### Export (PyTorch -> ONNX)

- Batch size must be exactly 1; export with `dummy_input = torch.randn(1, 3, H, W)` and check `shape[0] == 1` on every graph input. [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L8-L25]
- No dynamic shapes: do not pass `dynamic_axes` to `torch.onnx.export`; verify every input `dim_value > 0`. For several input sizes compile one `.dxnn` per size. [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L78-L103]
- Opset range 11-21 for DX-COM v2.5.0; opset 13 is the recommended choice. Check with `onnx.load(...).opset_import[0].version`. [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L107-L131]
- Always call `model.eval()` before export (training mode changes BatchNorm/Dropout topology). [dx-compiler@a087726ead v2.5.0: .deepx/agents/dx-model-converter.md#L29-L47]
- Use descriptive `input_names`; they must match the `inputs` key in config.json. Validate with `onnx.checker.check_model` and assert a single output when the model is an Ultralytics YOLO. [dx-compiler@a087726ead v2.5.0: .deepx/agents/dx-model-converter.md#L49-L72]
- Official export snippet (copied from the converter agent):
  ```python
  dummy_input = torch.randn(1, 3, 640, 640)  # Batch MUST be 1

  torch.onnx.export(
      model,
      dummy_input,
      "model.onnx",
      opset_version=13,           # Range: 11-21
      input_names=["images"],
      output_names=["output0"],
      dynamic_axes=None,          # MUST be None — DEEPX requires static shapes
  )
  ```
  [dx-compiler@a087726ead v2.5.0: .deepx/agents/dx-model-converter.md#L49-L62]
- Do NOT run onnx-simplifier automatically. Reasons given: FP32 rounding from constant folding, lost node names, possible graph breakage, and renamed input nodes that then mismatch config.json. Default flow is Export -> Validate -> Compile. If the user asks for it, re-check the input name afterwards. [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L212-L247] (agent rule)
- Ultralytics YOLO only (not ConvNeXt): manual `torch.onnx.export` yields 6 outputs unless `Detect.export=True`; prefer `model.export(format="onnx", ...)` or the one-shot `yolo export model=... format=deepx` (x86-64 Linux, detection only, INT8 enforced, output is a directory). [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L251-L325] [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L945-L966]
- Operator support rule relevant to LayerNorm-based nets (ConvNeXt uses LayerNorm): `LayerNormalization` is supported only over the last dimension (`axis=-1`, `Scale`/`B` shape `[D]`, D < 4080, otherwise runs on CPU); multi-dimension LayerNorm such as `nn.LayerNorm([C, H, W])` is not supported. LayerNorm decomposed into ReduceMean/Sub/Pow/Sqrt/Div/Mul/Add is supported when statistics are over a single dimension. [dx-compiler@a087726ead v2.5.0: source/docs/03_Building_Models.md#L49]
- If a model comes from another framework with an out-of-range opset, convert with the onnx version converter (`onnx.version_converter.convert_version(model, 13)`) when opset is out of range. [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L107-L131]

### Compile (DX-COM)

- Never fabricate dx_com calls; the correct import is `import dx_com` and `dx_com.compile(model=..., output_dir=...)`. There is no `dxcom.quantize()`, `dxcom.calibrate()`, `from dxcom import dxcom`, `model_path=`/`output=` kwargs, or `target_device`/`output_format`/`model_path` config keys. Read `toolsets/dxcom-cli.md`, `dxcom-api.md`, `config-schema.md` before generating calls. [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L802-L834]
- Banned parameter spellings: `output_path`, `model_path`, `calib_num`, `quant_device`; correct are `output_dir`, `model`, `calibration_num`. `SingleImageCalibDataset` and `CALIBRATION_OK` do not exist. [dx-all-suite@51d81fe2ef v2.5.0: .deepx/memory/sdk_grounding_reference.md#L107-L128]
- config.json `inputs` key must exactly match the ONNX input name (case and whitespace sensitive); shape must exactly match, batch 1, all dims positive; JSON config / `dxcom` CLI supports a single input only. [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/config-schema.md#L85-L95]
- `config=` and `dataloader=` are mutually exclusive in `dx_com.compile()`; with `dataloader=` pass calibration settings as keyword arguments. `dataloader` batch size must be 1. There is no `dx_com.DataLoader`; use `torch.utils.data.DataLoader`. [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L921-L943] [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/dxcom-api.md#L51-L52] [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/dxcom-api.md#L88-L96]
- `quantization_device` is deprecated in v2.5.0 and ignored with a `UserWarning`; use `--use_gpu {True,False}` / `use_gpu=` (default True = GPU when available, else CPU) and `CUDA_VISIBLE_DEVICES`. [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/config-schema.md#L229-L234] [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/dxcom-cli.md#L47-L52]
- Development invocation: add `--gen_log` and `--export_html` and review `<model>_summary.html` after every compile; add `--verbose` to expand masked errors; use `--opt_level 0` for fast iteration, `--opt_level 1` (default) for the final build. [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/dxcom-cli.md#L204-L212]
- Exit codes: only 0 = success is documented; do not rely on distinct non-zero codes. `DXCOM_LOG_LEVEL` is not a verified variable. [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/dxcom-cli.md#L186-L202]
- `--aggressive_partitioning` is experimental: maximises NPU ops but may increase compile time/memory and can give unexpected results; use with `--gen_log`. It does not offload to CPU. [dx-compiler@a087726ead v2.5.0: .deepx/instructions/compilation-workflow.md#L203-L208] [dx-compiler@a087726ead v2.5.0: .deepx/skills/dx-agent-compiler-compile/SKILL.md#L639-L649]
- The CLI is single-input only; multi-input models need the Python API with a DataLoader. The standalone `./dx_com/dx_com` executable is deprecated; use the `dxcom` command from the wheel (`pip install dx-com` inside a venv). [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/dxcom-cli.md#L7-L31]
- Do not generate PPU type 2 (deprecated since v2.4.0). `ppu` and `pre_optimize` are mutually exclusive in one config; v2.5.0 does not reject the combination, it silently falls back (see debugging). PPU/`pre_optimize` are YOLO-detection features and are irrelevant to a classifier. [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/config-schema.md#L267-L290] [dx-compiler@a087726ead v2.5.0: .deepx/skills/dx-agent-compiler-pre-optimize/SKILL.md#L132-L152]
- Never modify `compiler.properties` (since v2.5.0 it only holds `COM_VERSION`; it is sourced as bash by `install.sh`). Compile failures are always fixed in config.json, CLI args or the ONNX. [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L842-L890] (agent rule)
- QAT (`qmaster`) is opt-in only: needs a GPU, mutually exclusive with `use_q_pro`/`enhanced_scheme` (`EnhancementSchemeError`), unknown `qmaster` keys are silently ignored (check the Q-MASTER CONFIG box in compiler.log), `freeze_bn_after` must never be 0 (nan), and removed args `qat_config`/`qat_resume_from_checkpoint` are silently ignored. Run `fast_run` first and compare against PTQ on the same eval set. [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L998-L1012] [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/qat.md#L9-L10] [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/qat.md#L116-L118] [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/qat.md#L153] [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/qat.md#L257-L261]
- `--optimize_check` does not exist in the v2.5.0 CLI (argparse exit 2). [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/qat.md#L266]
- Accuracy escalation order, one step at a time with re-measurement: calibration method `ema` -> `minmax` -> `iqr`; then Q-PRO (`--use_q_pro` / `enhanced_scheme`, slow, opt-in); then `--quant_diagnosis` + QXNN `--checkpoint` resume; then QAT. [dx-compiler@a087726ead v2.5.0: .deepx/instructions/compilation-workflow.md#L168-L193]
- `--quant_diagnosis` writes `quant_diagnosis/diagnosis_report.html` and a `.qxnn` checkpoint; `--checkpoint x.qxnn -o out --recalibration_method iqr` re-quantizes without recompiling (resume-only flags error without `--checkpoint`). [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/dxcom-cli.md#L54-L68] [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/dxcom-cli.md#L157-L171]
- OOM during calibration: reduce `calibration_num` or quantize on CPU (`--use_gpu False`). [dx-compiler@a087726ead v2.5.0: .deepx/skills/dx-agent-compiler-compile/SKILL.md#L639-L649]
- Use a fresh working directory per session and keep all artifacts (onnx, config.json, .dxnn, compiler.log) together; do not scan previous sessions for reusable ONNX/DXNN files. [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L189-L209] [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L516-L545] (agent rule)
- Long compiles: run in the background with `start_new_session=True` and a `compile.pid`; poll with `kill -0 <PID>`, never `pgrep -f` (self-matching infinite loop). The agent file quotes 15-40 min compile time dominated by graph optimisation. [dx-compiler@a087726ead v2.5.0: .deepx/agents/dx-dxnn-compiler.md#L450-L513] [dx-compiler@a087726ead v2.5.0: .deepx/agents/dx-dxnn-compiler.md#L205-L212]
- Python environment: Ubuntu 24.04+ enforces PEP 668; always create/activate a venv before `pip install`, never use `--break-system-packages`. [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L549-L595] [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L714-L744]
- Compile can proceed on a host whose NPU init fails (dxcom runs on CPU), but NPU-based verification must then be recorded as SKIPPED, not PASS. [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L909-L915]
- Wheels: `manylinux_2_31_x86_64` (glibc >= 2.31), Python 3.8-3.14; x86-64 only (no ARM64 dx_com). [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/dxcom-cli.md#L17-L18] [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L961-L962]

### Calibration

- Calibration images must be representative of inference data (not random/synthetic/other domain); avoid duplicates; include variety. [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L55-L74]
- Defaults: `calibration_method="ema"` (lowercase only; `"EMA"` is rejected; alternatives `minmax`, `iqr`), `calibration_num=100`. The manual suggests trying several values (1, 5, 10, 100, 1000) and keeping the most accurate. If the dataset has fewer images than `calibration_num`, all are used without a warning. [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/config-schema.md#L105-L123]
- Real, multiple images from a directory are the official pattern; dataset class name is arbitrary; single-image augmentation is not the pattern. [dx-all-suite@51d81fe2ef v2.5.0: .deepx/memory/sdk_grounding_reference.md#L116-L121]
- `default_loader` reads images with `cv2.imread` (BGR, HWC, uint8) and applies `preprocessings` in order; it never transposes. For NCHW models (every PyTorch export incl. torchvision) end the chain with `{"transpose": {"axis": [2, 0, 1]}}` then `{"expandDim": {"axis": 0}}`; keep the final `expandDim` even for NHWC. Without it: `DataLoaderError: Invalid JSON Configuration for input ...`. [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/config-schema.md#L127-L142] [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/dxcom-cli.md#L214-L243]
- For RGB models whose mean/std are on a [0,1] scale (e.g. ImageNet), put `convertColor BGR2RGB` and `div 255` before `normalize`; ImageNet mean/std table is `[0.485, 0.456, 0.406]` / `[0.229, 0.224, 0.225]`. Use either the "Raw" std-255 row or `div 255`, not both. Operation `normalize` is `(x - mean) / std`. [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/config-schema.md#L186-L219]
- Official preprocessing chain example (YOLO, copied):
  ```json
  "preprocessings": [
    {"resize": {"width": 640, "height": 640}},
    {"div": {"x": 255}},
    {"convertColor": {"form": "BGR2RGB"}},
    {"transpose": {"axis": [2, 0, 1]}},
    {"expandDim": {"axis": 0}}
  ]
  ```
  [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L644-L653]
- `resize` width/height should match the spatial dims of the `inputs` shape; resize `mode` is `default` (OpenCV) or `torchvision` (PIL) and interpolation names must come from the same mode. [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/config-schema.md#L193-L211]
- `file_extensions` is required and matched case-sensitively (list `"JPG"` too for uppercase files); subfolders are searched. [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/config-schema.md#L180-L187]
- `dataset_path` resolves relative to the directory where compile is called, not the config file. Prefer relative paths for portability, or `os.path.abspath` when the call directory is uncertain; wrong path gives `DataNotFoundError`. [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/config-schema.md#L161-L177] [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L164-L185]
- Custom DataLoader route (multi-input, non-image, exotic preprocessing): return a CHW `float32` tensor from `__getitem__`; never `unsqueeze(0)` (gives `[1,1,C,H,W]`); `ToTensor()` scales to [0,1], so do not use it if the model expects 0-255; JSON `default_loader.preprocessings` is not used then, so match inference preprocessing by hand. [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L660-L707] [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/dxcom-api.md#L224-L229]
- If torchvision transforms are kept in a Dataset `transform` attribute, DX-COM may extract and fuse them; hand-written preprocessing in `__getitem__` gives `Fused ops: (none)`. Always read the INPUT PREPROCESSING GUIDANCE block in compiler.log. [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/config-schema.md#L147-L158]
- The compiler may bake `normalize`/`subtract`/`div` (and in some cases transpose) into the NPU graph. Every op listed on the `[INFO] - Added nodes:` line in compiler.log MUST be removed from host-side preprocessing, otherwise it is applied twice. [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/config-schema.md#L222-L228]
- QAT calibration/training data: never train on the set used to report final accuracy; if `default_loader.dataset_path` is missing, v2.5.0 silently falls back to a built-in ImageNet location, so verify the path exists. [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/qat.md#L221-L227]
- Agent-recommended sample calibration set is `dx_com/calibration_dataset/` (100 JPEG, downloaded from `https://sdk.deepx.ai/` by `example/2-download_sample_calibration_dataset.sh`); the agent itself notes it is generic and domain-specific data gives better accuracy. [dx-compiler@a087726ead v2.5.0: .deepx/instructions/compilation-workflow.md#L133-L147] [dx-compiler@a087726ead v2.5.0: .deepx/agents/dx-dxnn-compiler.md#L205-L233]

### Runtime (DX-RT / dx_engine)

- The compiled DXNN input format can differ from the ONNX input (NHWC `[1,H,W,3]` uint8 vs NCHW float32) because of bake-in. Always branch on `engine.get_input_tensors_info()` (`shape`, `dtype`) instead of hard-coding transpose/float conversion; for NHWC do not extract H,W from `shape[2:]`. [dx_app@375de0344f v3.3.0: .deepx/memory/common_pitfalls.md#L444-L515] [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L748-L798]
- `verify.py`-style comparison: use exactly the same preprocessing function for the ONNX and DXNN paths (RGB/BGR, interpolation, 0-255 vs 0-1, padding). [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L458-L486]
- Compare the ONNX run and the DXNN run on the same sample (detection count within 20%, class labels, bbox IoU were the agent's criteria for YOLO); never report success when this check fails. [dx-compiler@a087726ead v2.5.0: .deepx/memory/common_pitfalls.md#L419-L438] (agent rule)
- Call-name pitfalls verified against dx_engine source by dx_app: use `engine.run()` (not `infer`/`predict`), `get_input_tensors_info()[0]['shape']` (dict access, not `get_input_shape()` or dot access), `run_async()` returns `job_id` and `wait(job_id)` takes it, `Configuration().get_version()` (not `get_runtime_version()`), `DeviceStatus.get_device_count()` (not `list_devices()`), `dispose()` or context manager (not `close()`), `InferenceEngine(path)` constructor (not `load()`). `get_model_info()` does not exist; use `dxrt-cli --info model.dxnn`. [dx_app@375de0344f v3.3.0: .deepx/toolsets/dx-engine-api.md#L70-L110] [dx_app@375de0344f v3.3.0: .deepx/toolsets/dx-engine-api.md#L312-L330] [dx_app@375de0344f v3.3.0: .deepx/memory/platform_api.md#L358-L369]
- `InferenceOption` methods that exist: `set_use_ort`, `set_devices(list)`, `set_bound_option`, `set_buffer_count` (default 6, range 1-100); property syntax `option.devices = [0]` also works. `set_device_id`, `set_num_threads`, `set_batch_size`, `set_profiling`, `set_log_level` do not exist; batch size is fixed at compile time. [dx_app@375de0344f v3.3.0: .deepx/memory/common_pitfalls.md#L655-L699] [dx_app@375de0344f v3.3.0: .deepx/memory/performance_patterns.md#L383-L399]
- Always release the engine (`with InferenceEngine(...) as engine:` or `dispose()`); abnormal termination (kill -9, segfault) can leave the NPU locked; recover with `dxrt-cli --reset`. Install a SIGINT handler in custom scripts so Ctrl+C does not leave a zombie holding the device. [dx_app@375de0344f v3.3.0: .deepx/memory/platform_api.md#L143-L160] [dx_app@375de0344f v3.3.0: .deepx/memory/common_pitfalls.md#L166-L193]
- DX-RT older than 3.0.0 silently returns all-zero outputs with no error (the dx_app entry attributes it to `.dxnn` format v7 needing DX-RT >= 3.0.0); recompile `.dxnn` when upgrading DX-RT; check with `dxrt-cli -v` or `Configuration().get_version()`. [dx_app@375de0344f v3.3.0: .deepx/memory/common_pitfalls.md#L125-L148] [dx_app@375de0344f v3.3.0: .deepx/toolsets/dx-model-format.md#L120-L131]
- Sanity-check gate: run `bash scripts/sanity_check.sh --dx_rt` directly (no pipe to tail/head/grep) and judge by output text ("Sanity check PASSED!" and no `[ERROR]`), not exit code. If NPU "Device initialization failed", a cold boot is required; software install cannot fix it. This stop is unconditional even if the user says continue. [dx-runtime@73ff9904f5 v2.5.0: .deepx/memory/common_pitfalls.md#L200-L215] [dx-runtime@73ff9904f5 v2.5.0: .deepx/memory/common_pitfalls.md#L230-L246] (agent rule)
- Build order: dx_rt first, then dx_app, then dx_stream; missing dx_rt shows up as `cannot find -ldx_engine` or `gst-inspect-1.0 dxinfer` "No such element". [dx-runtime@73ff9904f5 v2.5.0: .deepx/memory/common_pitfalls.md#L176-L188]
- `run.sh` / `setup.sh` must use the same venv; `setup.sh` should fail hard (not warn) when `dx_engine` is not importable in the active venv. [dx_app@375de0344f v3.3.0: .deepx/memory/common_pitfalls.md#L746-L757]
- Headless hosts: guard `cv2.imshow` with a `DISPLAY`/`WAYLAND_DISPLAY` check; write images instead. [dx-runtime@73ff9904f5 v2.5.0: .deepx/memory/common_pitfalls.md#L101-L118]
- Model registry names are case-sensitive in `model_registry.json`; dx_app and dx_stream registries (`model_registry.json`, `model_list.json`) are independent and must be updated together. Not needed for our own custom pipeline unless dx_app is adopted. [dx-runtime@73ff9904f5 v2.5.0: .deepx/memory/common_pitfalls.md#L9-L13] [dx-runtime@73ff9904f5 v2.5.0: .deepx/memory/common_pitfalls.md#L164-L172]
- Recovery/diagnostics commands listed by dx_app: `lsmod | grep dx_npu`, `ls -la /dev/dx_npu*`, `dmesg | grep dx_npu`, `dxrt-cli --diag`, `dxrt-cli -s`, `dxrt-cli --reset`. [dx_app@375de0344f v3.3.0: .deepx/memory/platform_api.md#L318-L336]

### Performance

- Biggest Python-level lever: SyncRunner -> AsyncRunner (5 worker threads + main thread, SafeQueue maxsize 4) to overlap CPU work and NPU inference; SyncRunner remains right for single-image/debugging. Numeric FPS ranges in the same file are agent estimates (see Hypotheses). [dx_app@375de0344f v3.3.0: .deepx/memory/performance_patterns.md#L29-L60]
- Use `engine.run_benchmark(num_loops=...)` for FPS, and `get_latency()` / `get_npu_inference_time()` (microseconds) for latency; layer profiling via `Configuration().set_enable(Configuration.ITEM.PROFILER, True)` and `SHOW_PROFILE`. [dx_app@375de0344f v3.3.0: .deepx/memory/performance_patterns.md#L129-L175]
- Benchmark with `--no-display` to avoid display overhead in the measurement. [dx_app@375de0344f v3.3.0: .deepx/memory/performance_patterns.md#L229-L235] [dx_app@375de0344f v3.3.0: .deepx/memory/performance_patterns.md#L366-L381]
- If preprocessing ops are skipped by the compiler (transpose, resize, expandDim), they remain CPU MemoryOps on a single thread. Diagnose: `run_model -m model.dxnn -t 5 -v` vs the same with `--use-ort`; similar FPS means CPU-bound. Fix: `export DXRT_DYNAMIC_CPU_THREAD=ON`; look for `[DXRT] CPU TASK [cpu_0] ... Average Input Queue Load` above 50%. [dx_app@375de0344f v3.3.0: .deepx/memory/performance_patterns.md#L271-L333] [dx_app@375de0344f v3.3.0: .deepx/memory/common_pitfalls.md#L594-L653]
- Keep input uint8 when the model input is UINT8 to avoid float32 conversion; release frames promptly. [dx_app@375de0344f v3.3.0: .deepx/memory/performance_patterns.md#L334-L364]

### Debugging

- Compile fails: checklist in order: `onnx.checker`, `inputs` key vs ONNX input name, batch 1, no dynamic dims, opset 11-21, calibration path exists with images, `--gen_log` and read compiler.log, `--aggressive_partitioning` for unsupported ops, single ONNX output, contact DEEPX with compiler.log. [dx-compiler@a087726ead v2.5.0: .deepx/instructions/compilation-workflow.md#L422-L436]
- `--verbose` / `verbose=True` expands masked errors (e.g. "Unknown error occurred during compilation. - DX-COM error type names documented for diagnosis include `NotsupportedPaddingError` (asymmetric padding in width and height), `OnnxFileNotFound`, `RequiredLibraryError` (missing system library, e.g. `libgl1-mesa-glx`), and host-environment errors (`UbuntuVersionError`, `LDDVersionError`, `RamSizeError`, `DiskSizeError`). [dx-compiler@a087726ead v2.5.0: .deepx/toolsets/dxcom-api.md#L405-L412]
- The compilation summary report `<model>_summary.html` shows graph, NPU-vs-CPU partition, CPU-fallback reasons and I/O shapes; `grep -iE "npu|cpu|partition|fallback" compiler.log` gives machine-checkable partition evidence. - Misspelled/unknown keys are silently ignored by dx_com for `pre_optimize` and `qmaster` blocks; conflicts surface only as console lines like `falling back to legacy: ValueError: ...` with exit 0.
